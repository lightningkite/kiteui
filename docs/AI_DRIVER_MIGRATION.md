# AI Driver Migration Guide

## Overview

The AI driver system has been simplified from a typed JSON protocol to a plain-text command protocol. This reduces complexity, removes the need for serialization, and makes it trivially debuggable with `curl`.

## Architecture Changes

### Before: Three-tier JSON protocol

```
App ──(WebSocket/JSON)──► Daemon ◄──(HTTP/JSON)──► CLI
         :7474                         :7475
```

- Apps and daemon exchanged `AppMessage`/`DaemonMessage` sealed classes over WebSocket
- CLI sent `CliCommand` sealed classes to a separate HTTP port (7475)
- Daemon converted between the two protocols
- Required kotlinx.serialization for all message types

### After: Plain-text relay

```
App ──(WebSocket/text)──► Server ◄──(HTTP POST/text)──► CLI
                  :7474 (both)
```

- Single port handles both WebSocket (apps) and HTTP POST (CLI/tests)
- Server is a dumb relay: forwards text from CLI→app, returns text from app→CLI
- No serialization needed — commands and responses are plain strings
- CLI script auto-starts the server on first use

## What Was Removed

| Old Concept | Replacement |
|-------------|-------------|
| `AppMessage` sealed class | Raw text WebSocket frames |
| `DaemonMessage` sealed class | Raw text WebSocket frames |
| `CliCommand` sealed class | Plain text commands (e.g. `web-1 root snapshot`) |
| `CliFormat` decoder | Not needed — commands are just space-separated strings |
| `UiSnapshot` data class | Text snapshot output from `driverSnapshot()` |
| `UiComponent` data class | Text lines in snapshot tree |
| `UiAction` sealed class | Action strings dispatched by `driverActionPerform()` |
| `SnapshotWalkerBase` | `driverSnapshot()` + `driverDisplay()` on views |
| `ActionDispatcher` (per-platform) | `driverActionPerform()` on views + common code in `RViewHelper` |
| `ActionDispatcherCommon.kt` | Drag/drop logic moved to `RViewHelper.driverActionPerform()` |
| `AiDriverClient` | `AiDriver.connect()` (simplified) |
| Daemon (`Daemon.kt`, `CliServer.kt`, `AppSession.kt`, etc.) | `Main.kt` (~130 lines total) |
| `aiDriverTasks.kt` Gradle plugin | `installDriver` task in `ai-driver-server/build.gradle.kts` |
| Separate `/cli` HTTP endpoint (port 7475) | HTTP POST to same port as WebSocket (7474) |
| `CliCommand.Wait` | Use `UiTestScope.waitFor()` / `waitForText()` in test code |
| `CliCommand.Record` | Removed (can be re-added if needed) |
| `CliCommand.Find` with filters | `root find <query>` (simple text search) |
| `CliCommand.Mock` | Removed from CLI (use `MockExternalServices` in test code directly) |

## Command Format Changes

### Old: Typed CLI commands
```bash
kiteui-drive list
kiteui-drive snapshot web-1 --interactiveOnly --format text
kiteui-drive perform web-1 click submitBtn
kiteui-drive perform web-1 setValue emailField user@example.com
kiteui-drive perform web-1 navigate /dashboard
kiteui-drive perform web-1 back
kiteui-drive perform web-1 scroll container --dy -200
kiteui-drive wait web-1 --page HomePage --timeout 5000
kiteui-drive find web-1 --type Button --value "OK"
kiteui-drive logs web-1 --level Warn --lines 50
kiteui-drive screenshot web-1 --path debug.png
kiteui-drive mock web-1 file /path/to/photo.jpg
```

### New: Plain text
```bash
kiteui-drive ls
kiteui-drive web-1 root snapshot
kiteui-drive web-1 root snapshot --interactive
kiteui-drive web-1 submitBtn click
kiteui-drive web-1 emailField setValue user@example.com
kiteui-drive navigate /dashboard
kiteui-drive back back
kiteui-drive web-1 container scroll 0 -200
kiteui-drive web-1 root find OK
kiteui-drive logs 50
kiteui-drive web-1 root screenshot
```

Key differences:
- Commands target views directly: `<appId> <viewPath> <action> [args...]`
- `navigate` and `back` are top-level commands (not prefixed with `perform`)
- `ls` replaces `list`
- Snapshot options use `--interactive`, `--hidden`, `--themes` flags
- Scroll takes positional `dx dy` arguments
- No `--format` flag — output is always text

## Snapshot Format Changes

### Old: Structured `UiSnapshot` with `UiComponent`
```
Page: HomePage (/home)
navigatorView: SwapView
  0: Frame
    counter: Text = "0"
    increment: Button [click,longClick]
```

### New: Same text format, generated by `driverDisplay()`
```
0: Frame
  main: Column
    counter: Text = "0"
    increment: Button [click, longClick]
```

The format is nearly identical. Key differences:
- No `Page:` header line (use `navigate` to check/set current page)
- Generated directly by `RViewHelper.driverDisplay()` — each view renders its own line
- Actions set returned by `driverActions` on each view class

## App Integration Changes

### Old
```kotlin
// In your app's startup code
AiDriver.connect(
    appName = "myapp",
    platform = "web",  // or "android", "ios"
    host = "localhost",
    port = 7474,
    rootView = { /* return root RView */ },
    navigator = { /* return PageNavigator */ },
)
```

### New
Identical API — no changes needed:
```kotlin
AiDriver.connect(
    appName = "myapp",
    platform = "web",
    rootView = { /* return root RView */ },
    navigator = { /* return PageNavigator */ },
)
```

The only difference is that `connect()` now calls `tryAutoStartDaemon(port)` first, which auto-starts the server on JVM SSR. On Android/iOS/JS this is a no-op (the app connects to a server that should already be running or will reconnect when it starts).

## Driver Action Migration

### Old: `UiAction` sealed class dispatched through `ActionDispatcher`
```kotlin
sealed class UiAction {
    data class Click(val targetId: String) : UiAction()
    data class SetValue(val targetId: String, val value: String) : UiAction()
    data class Scroll(val targetId: String, val dx: Double, val dy: Double) : UiAction()
    data class DragAndDrop(val targetId: String, val toTargetId: String) : UiAction()
    // etc.
}
```

### New: Actions are strings on views
```kotlin
// In RViewHelper (base class)
open val driverActions: Set<String> get() = buildSet {
    if (dragData != null) add("getDragData")
    if (dropTargetDelegate != null) add("drop")
}

open suspend fun driverActionPerform(action: String, vararg args: String): String = when (action) {
    "snapshot" -> ...
    "scroll" -> ...
    "getDragData" -> ...
    "drop" -> ...
    else -> "ERROR: Unknown action"
}

// In Button (platform-specific)
override val driverActions get() = buttonDriverActions()  // returns setOf("click", "longClick")
override suspend fun driverActionPerform(action: String, vararg args: String) =
    if (action in driverActions) buttonDriverPerform(action, *args)
    else super.driverActionPerform(action, *args)
```

Each view type declares its own actions in `DriverOverrides.kt` (common code) and wires them in platform-specific view classes.

### Drag & Drop Changes

Old: Single `DragAndDrop(sourceId, targetId)` action that the dispatcher resolved.

New: Two separate actions with base64-serialized `DragData`:
1. `getDragData` on source view → returns base64 string
2. `drop <base64>` on target view → deserializes and invokes drop delegate

This is more flexible (data can be inspected/modified between steps) and works without the dispatcher needing to resolve two views simultaneously.

## Test Code Migration

### Old: `UiTestScope` with typed methods
```kotlin
uiTest(content = { /* UI */ }) {
    val snapshot: UiSnapshot = snapshot()
    val component: UiComponent? = find("submitBtn")
    click("submitBtn")
    setValue("email", "test@example.com")
    waitForPage("HomePage")
    assertValue("counter", "42")
    assertEnabled("submitBtn")
}
```

### New: `UiTestScope` with text-based methods
```kotlin
uiTest(content = { /* UI */ }) {
    val snap: String = snapshot()            // text tree
    val found: String = find("submit")       // text search results
    click("submitBtn")                       // returns "OK"
    setValue("email", "test@example.com")     // returns "OK"
    navigate("/home")                        // text-based navigation
    assertValue("counter", "42")             // checks snapshot text
    assertVisible("submitBtn")               // checks snapshot text
    waitForText("Welcome", target = "root")  // polls snapshot

    // New: scroll and drag/drop
    scroll("container", dy = -200.0)
    val dragData = getDragData("source")
    drop("target", dragData)
}
```

Key differences:
- `snapshot()` returns a `String` (text tree), not a `UiSnapshot` object
- `find()` returns a `String` (matching lines), not a `UiComponent?`
- `waitForPage()` → use `waitForText("PageName")` or `navigate("/route")`
- `assertEnabled()` / `assertDisabled()` → check snapshot text or action presence
- `assertValue()` checks for `= "value"` in snapshot text
- All action methods return `String` ("OK" or "ERROR: ...") instead of throwing

### Remote Testing

```kotlin
// Old
remoteUiTest(appId = "web-1", port = 7475) { ... }

// New
remoteUiTest(appId = "web-1", port = 7474) { ... }
```

Same API, but port changed from 7475 (old CLI-specific port) to 7474 (unified port).

## Server Setup Changes

### Old
```bash
./gradlew aiDriverInstall    # Gradle plugin task
kiteui-drive start           # Start daemon (ports 7474 + 7475)
kiteui-drive stop            # Stop daemon
kiteui-drive status          # Check status
```

### New
```bash
./gradlew :ai-driver-server:installDriver   # Build task
kiteui-drive start           # Start server (port 7474 only)
kiteui-drive stop            # Stop server
kiteui-drive ls              # Also auto-starts if not running
```

The CLI script now auto-starts the server on any command, so explicit `start` is rarely needed.

### ADB Reverse (New)

The server now automatically sets up `adb reverse` for connected Android devices. Every 5 seconds it checks `adb devices` and runs `adb reverse tcp:7474 tcp:7474` for new devices. This means Android apps can connect to `localhost:7474` without manual port forwarding.

### Auto-Start from JVM SSR (New)

When `AiDriver.connect()` is called on the JVM SSR platform, it automatically tries to start the daemon JAR at `~/.kiteui/ai-driver/kiteui-ai-driver.jar` if the server isn't running. This means JVM SSR tests can use the remote backend without manually starting the server.
